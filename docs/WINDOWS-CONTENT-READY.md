# 0.2.3：在内容画面出现后再交接

0.2.2 的窗口绑定与保留遮盖并不足以避免白底 Logo：启动器在窗口可见、响应、稳定后，就会显示实时缩略图。Codex 的启动页面也满足这些窗口条件。本次检查确认用户 MP4 的末帧是暗色角色画面，排除了“MP4 末帧本来就是白底 Logo”的解释；用户所见画面来自应用启动页面是当前推断，尚未捕获其实际发生的逐帧录像。

## 改动

新增 `WaitForContent`，默认 true。本测试包同时启用 auto 选屏和 BindToAppWindow。

- 在后台读取经过身份校验的目标客户端画面，仅在内存中缩小、分析分布；不保存截图、不读取聊天文本、不上传画面。
- 白/暗色平坦背景加中央 Logo 不授权显示实时缩略图或交接。需要连续两个具有分布式内容的样本，且样本仍新鲜；目标身份变化、画面退回空白或样本过期时撤销授权。
- 只有渲染证据通过，才显示实时缩略图；即便动画已结束，也继续保留遮盖并显示加载提示，直到内容就绪。总超时仍然有效。
- 若初选窗口仍停在启动画面，继续重新枚举前面的合格窗口，允许主窗口替换启动窗口。
- 无法捕获、捕获失败或超时时，不以“已经等了几秒”替代内容证据，而是在截止时间显示失败提示。用户可在配置中显式关闭 WaitForContent 恢复旧判定，但本包没有关闭。

这是一种针对中央 Logo/空白启动页的图像启发式，不是 Codex 官方内容就绪事件。复杂启动页可能误通过，极简正常界面也可能误拦截；尚不能保证消除所有白屏。它也不能阻止 Codex 在交接完成后自行重新加载页面。

画面读取采用 PrintWindow；其同步阻塞特性要求放到后台，WPF 线程只检查任务完成状态，避免阻塞播放器。参见 [Microsoft PrintWindow 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)。完整合成内容标志的用法参考 [Chromium 原生窗口快照实现](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/snapshot/snapshot_win.cc)。

## 验证范围

构建和标准自动测试：22 条几何/配置断言、64 条生命周期/多屏/画面就绪断言、33 条隔离入口断言通过；另有 605 个关键帧、12 个放置案例。新增白色空白、白底黑色中央 Logo、暗底亮色中央 Logo、分布式内容，以及两个样本、退回空白、过期和窗口替换授权撤销测试。

桌面宿主用真实已加载 Codex 验证后台捕获在遮盖窗口存在时可读取并识别内容，检查缩略图出现前已通过内容证据。开发阶段主副屏、自动选屏、绑定和受控冷窗口对齐通过；随后完整矩阵在短视频场景因 Windows 拒绝前台激活而失败，多次复测仍失败，不能把本版完整桌面测试标为通过。

新增受控的“窗口可响应但内容延迟到第 9 秒出现”和“画面一直不可用”路径：前者确认第 7 秒动画结束时继续遮盖、两个内容样本通过后才尝试交接，但最终激活仍被拒，因此只通过门控顺序测试，实际交接未通过；后者确认从不显示缩略图或尝试交接，在截止时间失败退出。

这些受控路径不等于真正重启 Codex。当前聊天依赖官方应用，没有强行终止它。最终仍需要以真实冷启动目视检查用户报告的白底 Logo，不能把已有实例或模拟测试成功说成已彻底解决。

最终 EXE 本机试运行确认内容探测和画面保留生效，但当时前台为 Explorer，系统拒绝自动激活 Codex，最终退出码为 2。因此本包标为诊断测试版，不能标为完整交接验证通过。

## 使用与回滚

关闭旧的社区启动器，解压本包后运行 DragonCodexBoot/DragonCodexBoot.exe。保留 MP4、配置和 EXE 的目录结构。原安装、快捷方式、官方 Codex 和旧测试包未覆盖。

日志新增 `content-probe ready=False/True` 与 `handoff-waiting-for-rendered-content`。复测时请保留完整日志，以便确定白底 Logo 出现在缩略图过渡期间、交接之前还是交接完成之后。

回滚仅需停止本包并使用上一版本；若正式部署过，应恢复备份的社区启动器 EXE 和配置。自定义 MP4 无需修改。
