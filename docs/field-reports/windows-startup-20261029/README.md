# Windows 启动动画稳定性案例：退出竞态、动画回放与原生入口边界

记录日期：2026-10-29（Asia/Shanghai）。本案例整理一次 Windows 实机排障和本地修改经验，供维护者复现、审查和选择性移植。

**范围声明：0.2.1 / 0.3.0 是本次本地构建的编号，不是上游发布版本。** 排障中经过多轮本地修改；下文明确确认的源码缺陷属于被审查的本地 0.2.1，不能直接归因于上游 `main`。本贡献不替换上游运行时代码，不发布 EXE、媒体、个人配置或原始客户端日志。

## 1. 用户观察与证据分级

用户进行了至少十次启动测试，只有两次完整无故障，观察到三种结果：

| 客户端状态 | 实际表现 | 能说明什么 |
|---|---|---|
| 后台已有可用实例 | 动画较流畅地交接到现有客户端 | 热启动路径可以工作，不足以证明冷启动正常 |
| 完全退出后再打开 | 动画停在“正在打开”画面，没有出现可用窗口 | 必须观察进程/包的收尾与后续实例，不能只看激活调用返回值 |
| 完全退出后再打开 | 客户端出现，但动画不结束，尾段再次播放 | 媒体完成状态与窗口就绪状态需要独立维护 |

2026-10-28 20:46:58–20:53:53 的本地日志包含 13 次启动器运行：6 次手动跳过后仍无窗口、2 次视频结束时未就绪且最后靠手动跳过交接、5 次记录自动交接。**自动交接日志不是用户实际成功率**，不能用它替代“只有两次无故障”的反馈。

未找到与这批测试对应的 Application 1000/1001/1002/1026 崩溃记录；这既不能证明客户端没有故障，也不能把每次窗口消失都解释为崩溃。先前的短期进程记录器已结束，没有覆盖这批失败，因而缺少对应激活 PID 的精确退出码。

### 包上下文与路径

本案例曾从打包应用上下文创建 `%LOCALAPPDATA%\DragonCodexBoot`。随后观察到启动器出现在包的 `LocalCache\Local` 路径，快捷方式解析结果也发生变化。改用长期保留的 `%USERPROFILE%\Documents\DragonCodexBoot` 独立目录后重新核对目标。此结论限定于本次上下文，不代表所有 LocalAppData 部署都会被重定向。

### 任务栏与原生入口

一个可写 `.lnk` 指向启动器，不等于原生 MSIX 搜索结果、任务栏缓存、直接 EXE 和协议入口全部经过启动器。2026-10-29 后续检查时，任务栏快捷方式目录已没有相应动画入口，不能把前一天替换成功的记录永久当作当前状态。

用户的最终需求是“打开原生安装的 ChatGPT 时自动播放动画”。本地 0.3.0 **仍是独立播放器再激活客户端**，没有实现原生应用内嵌，也没有实现从所有原生入口触发的持续监视器。本次任务栏操作未完成固定，不能记录成已接管原生任务栏入口。

## 3. 根因与局限

### 已确认：本地结束回退逻辑造成重播路径

被审查的本地 0.2.1 在 MediaEnded 时若窗口尚未就绪，会把播放位置设回 HoldAt；窗口重新就绪时又 Play。结束状态没有不可逆标记，因而可以重新播放尾段。日志存在“media-ended ready=False → window-available → 用户手动跳过”的对应时序；没有逐帧记录，不推断确切循环次数。

修复思路是无条件记住 `mediaFinished`，结束后只保留静态等待画面；交接条件为 `mediaFinished && targetUsable`，由主状态循环持续检查。不能只在 MediaEnded 的单个瞬间检查窗口。

### 高度符合：旧实例退出与新激活相遇

六次失败的 AppModel-Runtime 时序均表现为：旧实例开始释放资源，新激活进入同一旧应用容器，随后该旧容器结束。以其中一次为例，按旧实例开始释放资源归零：

```text
t=0.000 s   旧实例开始释放资源
t=1.982 s   新激活进入旧容器
t=5.389 s   相同旧容器结束
```

这高度符合退出/单实例交接竞态，但现有证据不足以判定具体内部锁、转发机制或退出代码。`ActivateApplication` 返回成功和 PID，不能直接解释为页面已打开；短命 PID 也可能是正常转交到继任实例，不能仅凭其退出盲目重启。

### 其他已发现的本地设计问题

- 80 ms 的单次响应探测失败会立即清空就绪，冷启动忙碌时容易反复稳定/失稳；需要记录超时、句柄销毁、候选变化等具体原因。
- 原本配置 60 s，但旧本地等待逻辑额外加了 20 s。用户在此前即手动跳过，不能称为已证实“无限等待”。
- 候选 HWND 变化但 DWM 缩略图不重新绑定，可能显示旧窗口；本批日志没有证实实际触发。
- `SetForegroundWindow` 请求和真实前台状态必须分开记录；发现窗口不等于用户已获得可操作前台。
- 最小化窗口恢复必须确认 `!IsIconic`；异步恢复请求被接受不等于恢复已经完成。

## 4. 本地 0.3.0 修改记录

| 部分 | 修改后的行为 |
|---|---|
| 媒体 | 只 Play 一次；完成状态不可回退；晚到窗口就绪后仍能交接，不重新播放 |
| 生命周期 | 观察实际包路径对应进程和稳定窗口；进程消失后等待 2 s 空档再激活；长期后台无窗口时有界观察 8 s |
| 补启动 | 最多一次，总激活不超过两次；仅在无窗口、无目标进程、未建立过就绪状态且未终止时允许 |
| 终止状态 | 完成、失败、取消不可返回激活/播放；忽略晚到回调；用户关闭已建立的客户端后不自动拉起 |
| 就绪 | 后台探测，至少三次响应和 1 s 稳定，短暂探测失联容忍；真实窗口销毁立即撤销 |
| 枚举不完整 | 不因其他不可访问的同名进程否决已核验目标 HWND；没有可验证窗口时仍禁止盲目启动 |
| 截止期限 | 安装配置统一 60 s；失败后释放覆盖层，普通提示 10 s 后自动退出 |
| 视觉过渡 | 暂停 DWM 实时嵌入与强制调整客户端尺寸，先使用完整视频和简单淡出；保留原生窗口尺寸 |
| 最小化 | 异步恢复一次，最多等 2 s 确认恢复和可见后交接 |
| 重复点击 | 单播放器，第二次点击仅发聚焦信号，不新增激活循环 |
| 日志 | 每次运行 ID、单调时间、激活次数/PID、退出码或不可获取原因、探测原因、媒体结束、交接请求及窗口/前台验证 |

这些观察与时间阈值是本地候选策略，仍需真实冷启动样本校准，不应作为所有 Windows 设备的固定标准。

参考策略保存在 [reference/LaunchLifecycle.cs](reference/LaunchLifecycle.cs)，对应离线故障场景在 [reference/LifecyclePolicyTests.cs](reference/LifecyclePolicyTests.cs)。它们是本地策略的可测试摘录，并不包含真实窗口探测、媒体播放或官方客户端集成。

## 7. 安全信誉提示与发布经验

用户曾看到“Windows 已保护你的电脑 / 更多信息”。本机重新构建文件在本次检查时没有 Zone.Identifier 下载标记，但未获得公开发行商签名；这不能保证将来下载、换设备或更新版本不再提示。本次未关闭 Windows 安全设置。启动可靠性和下载信誉是两个独立问题，不能用一次能运行来宣称信誉问题已永久解决。

安装应先备份程序和配置并核对目标，避免根据旧版 WindowsApps 路径恢复入口。本地替换脚本还遇到 Windows PowerShell 5.1 对 `[IO.File]::Replace` 空备份路径的兼容问题；显式指定备份文件后完成安装。不要把测试脚本、构建输出和用户机器专属部署脚本混为可直接发布的上游实现。
